# v1.5 Harness and Prompt Design Findings

> Context: This note summarizes the v1.5-dev evaluation observations after running early ICU-MUJICA Phase1 tests on GPT-5.5 and DeepSeek V4 Flash. It focuses on harness/prompt design weaknesses, not only model quality. It also records a proposed idea: vague requirements should preferentially trigger a clarification loop, and every request should maintain a datasheet-like design contract.

---

## 1. Why This Note Exists

The recent eval runs showed that model comparison alone is not enough.

Some failures looked like model weakness at first, but were actually caused by harness or runtime boundaries:

- LLM not actually entering the generation path, causing rule fallback and fake PASS.
- Internal Parser -> Generator timeout being too short for GPT-5.5.
- Provider transport errors such as SSL read failures.
- Architect schema repair or schema failure being mixed with ordinary model failure.
- Verify passing RTL that satisfied the generated SpecReg but not necessarily the original user request.

This means the current v1.5 harness is useful, but it is still closer to:

```text
LLM generation + schema validation + compile check + artifact logging
```

than to a full requirement-preserving design harness.

The next useful step is not just adding more benchmark cases. We should first tighten the harness contract around:

```text
raw user request
  -> clarification / assumptions
  -> datasheet-like design contract
  -> SpecReg
  -> RTL
  -> structural + behavioral verification
  -> trace/error classification
```

## 2. Current Observed Problems

### 2.1 Verify Checks the Generated SpecReg, Not the Original Request

Current flow:

```text
raw user prompt
  -> Parser / Architect
  -> SpecReg
  -> Coder
  -> Verify against SpecReg
```

The risk is that Architect may simplify, omit, or silently reinterpret the original request. If that happens, Verify can still pass because it checks RTL against the generated SpecReg, not directly against the raw prompt.

Failure shape:

```text
Original request contains constraints A, B, C, D
  -> SpecReg keeps only A and B
  -> RTL satisfies A and B
  -> Verify PASS
  -> but original request was not satisfied
```

This is especially dangerous for fuzzy prompts and complex multi-module prompts.

Suggested improvement:

```text
Add Spec Coverage Check:
raw request key constraints -> must appear in SpecReg or assumptions/clarifications.
```

For each eval case, we can maintain a small `must_cover` list. Example for `rr_arbiter4`:

```text
- enable=0 clears grant/valid/idx but holds last_grant_dbg
- no request clears grant/valid/idx but holds last_grant_dbg
- priority starts after last_grant_dbg
- last_grant_dbg resets to 3
- grant is one-hot
```

The first version can be keyword/rule based. It does not need an LLM judge at first.

---

### 2.2 Fallback Was Too Quiet

A previous invalid eval run produced very fast fake passes. The RTL looked like a rule fallback template:

```verilog
module some_top(
    input wire i_clk,
    input wire i_rst_n,
    output reg o_done
);
...
endmodule
```

This happened while the eval expected LLM generation. The result passed basic structural verification but was obviously not a valid model result.

The runner now records:

```text
parser_chat_count
architect_chat_count
coder_chat_count
verify_chat_count
invalid_llm_not_used
```

This should be promoted from runner-only logic into the harness itself.

Suggested improvement:

```text
generation_mode:
  - llm
  - llm_with_schema_repair
  - rule_fallback
  - llm_failed
  - retry_generated
```

Any fallback path must be explicit in artifacts and in final result. Silent fallback should not be allowed to count as a model PASS.

---

### 2.3 Error Classes Are Mixed Together

Current errors can include very different causes:

```text
- model produced invalid JSON
- schema repair failed
- provider SSL/read error
- internal HTTP timeout
- compile fail
- semantic fail
- testbench fail
- LLM not used
```

But currently they can all surface as generic workflow errors.

Observed examples:

- GPT-5.5 `C02_rr_arbiter4` initially timed out around the Generator timeout boundary. After increasing service timeout, it passed Verify and supplemental TB.
- GPT-5.5 `C04_pwm_generator` failed twice with `[SSL: DECRYPTION_FAILED_OR_BAD_RECORD_MAC]`, a transport/provider error during Architect LLM response reading.
- DeepSeek V4 Flash completed the same small batch faster and with fewer schema repair events.

Suggested improvement:

```text
error_class:
  - success
  - invalid_llm_not_used
  - parser_schema_error
  - architect_schema_repair_success
  - architect_schema_failure
  - coder_generation_failure
  - transport_error
  - timeout_error
  - verify_compile_fail
  - verify_semantic_fail
  - supplemental_tb_fail
  - user_clarification_required
```

This classification is important for fair model comparison and for future self-evolution. A provider SSL failure should not be learned as a model design weakness.

---

### 2.4 Prompt and Schema Contracts Are Not Fully Aligned

GPT-5.5 often produces richer SpecReg content, but also frequently triggers Architect repair. DeepSeek V4 Flash tends to produce shorter, more schema-stable SpecRegs.

Observed pattern:

```text
GPT-5.5:
  - richer functional requirement expansion
  - more corner cases
  - slower
  - more ArchitectRepairFrame events
  - clock_and_reset often missing

DeepSeek V4 Flash:
  - shorter SpecReg
  - fewer schema repairs
  - faster
  - sometimes less descriptive ports / assumptions
  - code may be more compact or more implementation-driven
```

This suggests prompt/schema design is not only measuring model quality; it is also shaping model failure modes.

Possible improvements:

1. Separate requirement extraction from strict schema filling.

```text
Pass 1: extract requirements, assumptions, open questions
Pass 2: fill strict SpecReg schema
```

2. Add stronger field consistency requirements.

```text
If a clock/reset exists:
  - include it in clock_and_reset
  - mark relevant ports is_clock/is_reset
  - make reset polarity/type consistent across all fields
```

3. Use a smaller explicit schema contract in the prompt rather than relying on a very broad implicit model of SpecReg.

4. Treat unknown/ambiguous items as assumptions or clarification requests, not silent defaults.

---

### 2.5 Fuzzy Requirements Are Currently Treated Too Much Like Complete Specs

A vague request such as:

```text
Write a simple PWM module with clk/reset, duty and period, output pwm_out.
```

contains missing decisions:

```text
- duty/period width
- reset polarity
- reset synchronous/asynchronous
- period=0 behavior
- duty>=period behavior
- registered or combinational output
- enable or no enable
```

Current behavior may silently choose defaults. For example, DeepSeek's `pwm_generator` assumed:

```text
- reset is synchronous active-high
- duty/period are 8-bit
- period=0 not explicitly handled
```

The RTL was compilable and basic, but the assumptions were not made prominent enough.

This is not necessarily a bad model output; the harness should decide whether vague input may proceed or should require clarification.

## 3. Proposed Idea: Clarification-First Flow for Vague Requirements

For vague or under-constrained requests, the system should preferentially trigger a clarification loop before generation.

The goal is not to annoy the user with unnecessary questions. The goal is to avoid silent design choices becoming hidden bugs.

### 3.1 Add an Ambiguity Detector

Parser/Architect should classify the request:

```text
requirement_clarity:
  - complete
  - mostly_complete
  - ambiguous_but_usable
  - clarification_required
```

Example ambiguity categories:

```text
clock_reset_ambiguity
width_ambiguity
protocol_ambiguity
state_behavior_ambiguity
edge_case_ambiguity
multi_module_architecture_ambiguity
parameterization_ambiguity
verification_expectation_ambiguity
```

For each ambiguity, record:

```json
{
  "field": "reset",
  "issue": "reset polarity and sync/async behavior not specified",
  "default_candidate": "synchronous active-high reset",
  "risk": "generated RTL may not match user's target environment",
  "clarification_question": "Should reset be synchronous or asynchronous, and active-high or active-low?"
}
```

### 3.2 Clarification Policy

A simple policy:

```text
If ambiguity affects interface, state semantics, reset, protocol, CDC, FIFO, ordering, or safety:
  -> ask clarification before RTL generation.

If ambiguity is low-risk and conventional:
  -> proceed, but record assumption in datasheet.
```

Examples:

Ask clarification:

```text
- reset type missing for sequential module
- width missing for externally visible data path
- valid-ready behavior underspecified
- FIFO simultaneous read/write behavior missing
- CDC pulse behavior missing
- multi-module architecture boundaries unclear
```

Proceed with assumptions:

```text
- default output value in no-request combinational encoder
- internal register naming
- non-user-visible implementation style
```

### 3.3 Clarification Should Produce a Durable Design Datasheet

The user's current idea: whether the request is vague or clarified, the system should maintain something like a datasheet.

This is a strong direction.

The datasheet is not just a summary. It is the persistent design contract that sits between raw user intent and SpecReg/RTL.

Proposed artifact:

```text
DesignSheet.md / DesignSheet.json
```

It should be created for every task, not only fuzzy requests.

## 4. DesignSheet Concept

### 4.1 What DesignSheet Is

DesignSheet is a datasheet-like living contract for the generated design.

It records:

```text
- user intent
- interface
- clock/reset
- parameters
- protocol
- behavior
- assumptions
- unresolved questions
- clarified answers
- verification expectations
- generated module structure
- known limitations
```

It should be readable by humans and structured enough for tools.

### 4.2 Why DesignSheet Helps

It solves several current problems:

1. Prevents silent assumptions.
2. Provides a stable target for Architect and Coder.
3. Lets Verify check against user-level intent, not only generated SpecReg.
4. Gives future self-evolution a cleaner trace artifact.
5. Makes fuzzy prompts first-class rather than accidental.

Current flow:

```text
raw prompt -> SpecReg -> RTL
```

Proposed flow:

```text
raw prompt
  -> ambiguity detection
  -> clarification if needed
  -> DesignSheet
  -> SpecReg
  -> RTL
  -> Verify against SpecReg + DesignSheet coverage
```

### 4.3 Suggested DesignSheet Fields

Example JSON shape:

```json
{
  "design_name": "pwm_generator",
  "clarity": "ambiguous_but_usable",
  "intent": "Generate a simple PWM output based on duty and period.",
  "interface": {
    "ports": [
      {"name": "clk", "direction": "input", "width": 1},
      {"name": "rst_n", "direction": "input", "width": 1},
      {"name": "duty", "direction": "input", "width": 8},
      {"name": "period", "direction": "input", "width": 8},
      {"name": "pwm_out", "direction": "output", "width": 1}
    ]
  },
  "clock_reset": {
    "clock": "clk",
    "reset": "rst_n",
    "reset_type": "async_low",
    "source": "clarified_by_user"
  },
  "parameters": [],
  "behavior": [
    "counter increments each cycle while not reset",
    "counter wraps at period-1",
    "pwm_out is high when counter < duty"
  ],
  "edge_cases": [
    {"case": "period == 0", "behavior": "force pwm_out=0 and counter=0"},
    {"case": "duty >= period", "behavior": "saturate pwm_out high when period != 0"}
  ],
  "assumptions": [
    {
      "item": "duty and period width",
      "choice": "8-bit",
      "source": "default_policy",
      "risk": "may not match target design if user expected wider counter"
    }
  ],
  "clarification_questions": [],
  "verification_expectations": [
    "reset drives pwm_out low",
    "duty=0 keeps pwm_out low",
    "period=0 handled explicitly"
  ]
}
```

### 4.4 DesignSheet for Clarification Loop

For unclear requests, first artifact could be:

```json
{
  "clarity": "clarification_required",
  "blocking_questions": [
    {
      "id": "Q1",
      "question": "Should reset be synchronous or asynchronous, active-high or active-low?",
      "choices": ["sync_high", "sync_low", "async_high", "async_low"],
      "default_if_unanswered": "sync_high",
      "risk": "Reset style changes RTL sensitivity list and integration behavior."
    },
    {
      "id": "Q2",
      "question": "What width should duty and period use?",
      "choices": ["8", "16", "parameterized"],
      "default_if_unanswered": "8",
      "risk": "Width changes counter size and interface."
    }
  ]
}
```

If the user answers, DesignSheet is updated:

```text
Q1 answered -> reset_type = async_low, source = user_clarification
Q2 answered -> width = parameterized, source = user_clarification
```

If user chooses not to answer, DesignSheet records defaults explicitly:

```text
source = default_policy
```

This makes ambiguity visible and auditable.

## 5. Where DesignSheet Fits in v1.5

A possible v1.5 flow:

```text
Parser
  -> request classification
  -> ambiguity detection
  -> DesignSheet draft
  -> if clarification_required: return questions / pause
  -> else continue

Architect
  -> consume DesignSheet
  -> produce SpecReg
  -> preserve assumptions and clarified fields

Coder
  -> consume SpecReg + DesignSheet
  -> generate RTL
  -> include major assumptions in comments when appropriate

Verify
  -> check RTL vs SpecReg
  -> check SpecReg coverage vs DesignSheet
  -> run compile / TB / structure checks
```

This keeps Parser from being only an intent router. Parser becomes the entry point for information cleaning.

## 6. How This Relates to Harness

Earlier we described harness as:

```text
permission cleaning + information cleaning + trace/feedback structuring
```

DesignSheet is the missing information-cleaning artifact.

Instead of throwing raw prompt directly into Architect, we create a cleaned, explicit, auditable design contract.

This also helps future self-evolution:

```text
raw prompt + clarification + DesignSheet + SpecReg + RTL + VerifyRpt + TB result
```

becomes a much better trace than:

```text
prompt + generated RTL + compile result
```

The system can later learn patterns such as:

```text
PWM requests often omit period=0 behavior -> ask or default explicitly.
FIFO requests often omit simultaneous read/write semantics -> ask before generation.
CDC requests often omit pulse frequency guarantees -> clarification required.
Multi-module requests often omit module ownership boundaries -> require architecture contract.
```

This is close to the user's self-evolution direction: repeated ambiguity/failure patterns can become new evaluator triggers or clarification templates.

## 7. Proposed Improvements in Priority Order

### P0: Result Validity and Error Classification

Already partly started in eval runner.

Add to system artifacts:

```text
generation_mode
error_class
invalid_llm_not_used
llm_transcript_presence
transport_error vs schema_error vs verify_error
```

### P1: Ambiguity Detection and Clarification Gate

Before generation, classify whether request can safely proceed.

Output:

```text
clarification_required | proceed_with_assumptions | complete
```

For clarification-required cases, return questions instead of generating RTL immediately.

### P2: DesignSheet Artifact

Create and persist:

```text
DesignSheet.json
DesignSheet.md
```

The Markdown version is for human review; JSON is for tools.

### P3: Spec Coverage Check

Check whether SpecReg covers DesignSheet key requirements and assumptions.

First version can be case/rule based.

### P4: Multi-Module Structure Check

For architecture-heavy cases such as Cextra:

```text
required modules present
required instance counts
required parameters
top-level wiring hints
compile all rtl_paths
```

### P5: Stronger Supplemental TB / Behavioral Smoke

Especially for fuzzy cases, add edge-oriented tests:

```text
period=0
reset behavior
duty=0
duty>=period
out_ready stall
FIFO full/empty
```

## 8. Cextra Implication

The proposed Cextra should not be just a large natural-language RTL request.

It should be an architecture contract test:

```text
- required module definitions
- required instance counts
- required parameter names
- required FSM states
- required top-level connection map\n- required behavior smoke tests
```

This is necessary because we specifically want to test model planning, not just whether it can emit a long Verilog file.

Suggested direction:

```text
Cextra_stream_router2_param_fsm
```

It should test:

```text
1 top + multiple submodules
parameterized reusable FIFO instantiated twice
frame receive FSM
round-robin output arbitration
valid-ready output behavior
multi-file compile
structure checker
behavioral smoke TB
```

---

## 9. Short Takeaway

Current ICU-MUJICA v1.5 can already generate RTL, run compile checks, archive traces, and compare model profiles.

But recent tests show that harness and prompt design still need a stronger contract layer:

```text
raw request
  -> ambiguity detection
  -> clarification or explicit assumptions
  -> datasheet-like DesignSheet
  -> SpecReg
  -> RTL
  -> coverage + compile + behavior checks
```

The key idea to carry forward:

> For fuzzy requirements, do not silently guess important design semantics. Prefer triggering a clarification step. Whether clarified or defaulted, maintain a datasheet-like artifact that records the design contract, assumptions, open questions, and verification expectations.

This turns vague natural language from a hidden risk into a first-class part of the harness.
