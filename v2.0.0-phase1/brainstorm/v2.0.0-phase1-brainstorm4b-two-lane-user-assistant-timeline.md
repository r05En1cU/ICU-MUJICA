# 1. 2026-05-29 06:22 — `ICUMUJICA Agent 完结`

对应文件：`vision-gpt-chat/ICUMUJICA Agent 完结_6700b73a878a (2).md`

---

## User 线

这一段的 User 线一开始并不是理论问题，而是项目状态：

```text
ICUMUJICA Agent Ver. 完结。
```

随后用户补充项目全称：

```text
IC Unified Multi-agent unified joint IC automation
```

里面的 `M` 最初主要指 Multi，既可以是 Multi-agent，也可以在后续版本里理解成 Multi-skill。

这时用户的起点比较明确：

- v1 multi-agent 版本已经做完；
- v1 不是完全失败，“做得还算可以”；
- 但只是“能用”的水平；
- 真正性能还是受限于 LM 智力；
- 分工虽然明确，但成效没有让人满意。

然后 User 线开始出现第一个转向：

```text
原本依靠 jinja2 传递多 system prompt 的多 Agent 体系，
全面换成 skill 体系。
```

这个转向里有几个用户侧的隐含判断：

1. 多 system prompt 已经有点 skill 化；
2. multi-agent 的收益不够；
3. skill 可能比 agent 更适合长期工程化；
4. 现有 agent 主要是 harness 工程，但 skill 也许可以做到类似效果。

用户并不是一开始就说“我要做 Graph Evolution”。当时更像：

```text
v1 multi-agent 已经结束，v2 也许该从 agent 切换到 skill。
```

随后 User 线开始插入 HDL 本体表示的问题。

用户先说：

```text
tokenize 的语言对 HDL 或至少 HD 来说不太合适。
```

然后进一步说：

```text
比起 AST，还是 graph 更合适，HDL 的 tree 属性没有那么强。
```

再然后用户修正了 assistant 对“agent graph”的理解，强调自己说的 graph 不是 workflow graph，而是 HDL 本身的 graph：

```text
端口是节点，逻辑是边，边又可分为节点和边，直到 sequential 为止。
```

这句话在 User 线里很关键。因为它不是在说 agent 怎么组织，而是在说 HDL 的表示应该递归地 graph 化。

同一段里，User 线还出现了“可训练 skill”的早期版本：

```text
训练不是梯度下降，而是 LM 对话时微调 System Prompt。
```

这时用户关注的不是模型训练，而是 skill 在运行中根据经验改变自身规则。

最后，User 线提出“切成臊子”和小粒度 skill：

```text
小粒度更好做，更好优化，也好做类似 MOE 的东西。
```

所以 5 月 29 日这一段，User 线从项目完结分享，移动到：

```text
multi-agent 不满意
    ↓
想转 skill
    ↓
HDL 应该 graph-first
    ↓
skill 可以运行时调整
    ↓
小粒度 skill / 类 MoE
```

这条线还没有出现“mutation”这个词，但已经有后面所有东西的胚胎。

---

## Assistant 线

Assistant 线一开始主要是在解释为什么 multi-agent 没有带来质变。

它的第一层回应是：

```text
Agent 数量 ≠ 智力提升。
```

模型把用户的不满意解释为 agent engineering 的普遍问题：

- 多个 agent 不会自动增强底层 LM；
- 很多多 agent 系统只是多个模型互相 reinforcement hallucination；
- 有价值的 multi-agent 更多来自状态隔离、工具职责固定、context compression；
- IC automation 对长链条一致性、约束、工具调用、error recovery 要求很高。

接着，Assistant 线把用户的“换成 skill”解释成：

```text
从角色模拟转向能力接口化。
```

它把多 system prompt 的问题说成：

- 能力边界不稳定；
- prompt orchestration 难 scale；
- system prompt 不是真正 abstraction；
- skill 更容易做 deterministic validation；
- skill graph / capability graph 会更像真正 automation framework。

这一段 assistant 线已经开始把用户的工程直觉抬高一点：

```text
multi-agent chat
    ↓
capability interface
    ↓
skill graph / capability graph
```

当用户谈 HDL tokenizer 时，assistant 线把问题改写为：

```text
HDL 不适合被当成 token sequence 建模。
```

它从“tokenizer 不合适”推到：

- HDL 是强结构、强时序、强约束；
- 语义单位不等于 token 单位；
- HDL 更接近 AST / IR / netlist graph / dataflow graph；
- LLM pretraining objective 和 HDL 语义结构不在一个空间。

当用户说 AST 不如 graph 时，assistant 线进一步把 HDL graph 分成：

- Dataflow Graph；
- State Transition Graph；
- Timing Graph。

当用户说 agent 版底层已经是 graph 时，assistant 一开始误把它理解成 agent workflow graph，随后被用户纠正。纠正后，assistant 线把用户的 HDL graph 解释成：

```text
recursive computational graph / hierarchical hypergraph / graph rewriting system
```

并指出 sequential element 是 cut boundary。

在可训练 skill 这部分，assistant 线把用户的想法推成：

```text
runtime-adaptive capability module
```

它强调：

- System Prompt 也是一种状态；
- prompt mutation 会导致 semantic drift；
- skill 的训练可能更新 execution policy、attention bias、context shaping、routing preference。

在“小粒度 skill + MoE”这部分，assistant 线把它解释成：

```text
Semantic / Structural MOE
```

并把 expert 从神经网络 block 换成 skill operator。

这时 Assistant 线的特点是：

- 很擅长把用户的工程表达抽象成更大概念；
- 逐步提出 capability graph、graph operator、semantic MOE 这些词；
- 还没有明显把用户推入 mutation / fitness / theorem 层，但已经开始把话题往“系统本质”方向抬。

## User 线


这时 User 线的状态不是“我要做完整 graph evolution”，而是：

- skill 系统到底用现成框架还是自己搓；
- 初期是不是需要 LangGraph；
- 如果只验证 skill / prompt fragment / retrieval，轻量实现可能更合适。

接着用户把 ICU-MUJICA v2 文档贴出来：

```text

放弃 v1 多 docker 和多 agent

```

这份文档里，User 线已经明确了 v2 的几条主线：

- 多轮对话；
- 前端设计、仿真、后端参与；

但是用户也说：

```text

```

这一段 User 线其实是在把 v2 的“方向”先写下来，还没有决定底层到底是 skill registry、workflow DAG、pass manager、graph runtime，还是 evolution graph。

---

## Assistant 线

Assistant 线先做 skill 概念史梳理。

它把 skill 分成几类：

1. RL 里的 skill / option / macro action；
2. Tool use 时代的 skill ≈ tool；
3. Voyager 式 reusable program skill；
4. Prompt fragment / context transformer 式 skill。

这让用户的 skill 想法获得了多个可能位置。

当用户犹豫 LangGraph vs 自己搓时，assistant 线没有直接推荐框架，而是重新定义初期问题：

```text
如果目标是验证 Skill = Prompt Fragment / Context Transformer，
第一版可以自己搓。
```

它把最小问题压成：

```text
Skill 如何表示
Skill 如何检索
Skill 如何组合
```

并提出：

```text
Task → Embedding/BM25 → Top-K Skills → Prompt Assembly → LLM
```

这里出现了一个重要词：

```text
RAG for Behavior
```

也就是检索的不是事实知识，而是解决问题的方法。

当用户贴 v2 文档后，assistant 线把 ICU-MUJICA v2 解释成：

```text
v1: Multi-Agent Everything
v2: Single LLM + Skill + Workflow
```

然后进一步说它更像 compiler pipeline，而不是 chat agent。

它提出几个映射：

```text
Skill = Operator
Workflow = DAG / Pipeline
Artifact = IR
Workspace = Build Directory
RAG = Design Database
```

甚至建议 `workflow/` 也许更像 `passes/`。

Assistant 线在这里主要做了两件事：

1. 把用户的 skill 想法从社区术语里定位；
2. 把 v2 文档从“没头绪”解释成“缺抽象层”。

它把 ICU-MUJICA v2 暂时推向：

```text
HDL Compiler + LLM Passes + Skill Library
```

这不是最终答案，但后续很多 discussion 都在这个坐标系里展开。

## User 线

User 线一开始问 LoRA 类微调方法。

这看起来像模型训练问题，但很快转向 Skill Graph：

```text
参考 2605.12039 的 skill graph。
论文提到 graph 结构需要用 GRPO 重新训练。
用户感觉 LoRA 也能获得类似效果。
```

这时用户想弄清楚：

- GRPO 学的到底是什么；
- LoRA 能不能替代；
- 如果 skill graph 是 policy / routing，是否一定要 RL；
- 是否可以用更便宜的方法获得 graph traversal / skill selection 能力。

随后用户把想法接到分层记忆机制：

```text
RAG 做长期记忆；
shared workspace 和 project 单次对话 md 做中短期记忆；
中间插入 Graph 记忆。
```

User 线此时的结构是：

```text
长期历史 / 文档 / 案例
    +
当前项目上下文
    +
Graph 记忆存范式
```

用户接着提出 Evaluate + Execute：

```text
Graph node 可以是 evaluate + execute 两类组合。
Evaluate 返回问题类型和位置；
根据类型和位置决定执行哪类 execute。
```

这个想法在用户侧还比较自然语言，但已经有了很清晰的方向：

- evaluate 负责判断；
- execute 负责动作；
- evaluate 不一定只返回问题类型，也可以返回建议；
- graph 不是单纯 skill list，而是诊断/行动结构。

最后用户提出老师关于 memory 的观点，并反驳：

```text
不能做的东西喂给 LLM 效果可能不好；
不如练到自定义 Linter 里面做成硬约束。
```

这里 User 线自己把“软记忆”和“硬规则”分开了。

```text
Graph 负责记忆；LLM 负责决策。
```

然后，assistant 线把用户的分层记忆接到 MemGPT / A-MEM / GAM / cognitive memory：

```text
Episodic Memory
Semantic Memory

```

并指出 procedural memory 已经接近 skill。

Assistant 线在这里给出一个较大的结构：

```text

    ↓

    ↓

    ↓
```

当用户提出 RAG / workspace / graph memory 时，assistant 线把它重新表达成：

都被放进一个分层 agent memory / decision system 里。

# 5. 2026-06-04 12:42 — `Graph结构优化思路`

## User 线

User 线从一个具体例子开始：

```text
LLM 输出 RTL 功能完备，但是缺少模块复用；
reasoning 和 output 偷懒；
经过反馈后，LLM 询问是否需要检查模块复用 / 可配置性，
然后加入这个 graph 节点作为设计初期评估 skill。
```

这个例子非常重要，因为用户第一次把 feedback → graph update 说得比较具体。

然后用户尝试定义进化：

```text
在不发生系统复杂度爆炸的情况下，性能能提高。
```

这说明 User 线不是想让 graph 无限变大，而是在寻找一种可持续改进。

接着用户列出可优化对象：

- Skill prompt；
- Graph 结构；
- 参数；
- RAG 代表性项目；
- 只保留 top 项目。

这里 User 线把 evolution 对象从 graph 扩展到整个 agent system。

随后用户强调：

```text
至少是可持续的。
```

又进一步说：

```text
理想情况下只留必要组件，其他针对模型能力自动生成。
```

再后来，用户承认基础 planning 更多依赖预设：

```text
这和之前设想的可进化系统差不多，
但是基础 planning 更多依赖预设。
```

最后用户把 ICU-MUJICA 和 Codex / Claude Code 对比：

```text
这些 coding agent planning 能力更好，
完全可以用 dynamic skill 或 harness。
```

这说明 User 线开始担心：如果模型 runtime planning 已经足够强，那么自己设计 skill graph / workflow evolution 的独特性在哪里。

---

## Assistant 线

Assistant 线先把用户的例子解释成：

```text
Graph 结构优化 / Workflow Learning
```

而不是 capability learning。

理由是：模型本来知道复用性，只是 workflow 没触发检查。

这时 assistant 线提出：

```text
学习的不是不会 → 会，
而是知道但没做 → 下次记得做。
```

随后它警惕 graph 爆炸，建议优先更新触发条件，而不是每次新增节点。

当用户定义“进化”为性能提升且复杂度不爆炸时，assistant 线把它形式化成：

```text
Evolution Score ≈ ΔPerformance / ΔComplexity
```

并提出三种更新成本：

```text
Level 1: Prompt / Parameter update
Level 2: Routing / Strategy update
Level 3: Graph structure update
```

当用户列出 skill、graph、RAG、参数等多种优化对象时，assistant 线把它整理成多层 evolution：

```text
Skill Evolution
Parameter Evolution
Routing Evolution
Memory Evolution
RAG Evolution
Graph Evolution
```

当用户说“可持续”时，assistant 线强调：

```text
优先修改已有组件，而不是新增组件。
```

并把每种修改赋予成本：

```text
Prompt 优化 < 参数调整 < Routing 调整 < RAG 调整 < Graph 修改 < 新增 Skill
```

当用户说只留必要组件时，assistant 线提出：

```text
Minimal Core + Generated Layer
```

并给出一个很重要的原则：

```text
系统复杂度应该与模型能力负相关。
```

当用户承认 planning 需要预设时，assistant 线给出：

```text
Foundation Layer + Evolution Layer
```

也就是固定骨架、演化实例。

最后，在 Codex / Claude Code 对比中，assistant 线指出：

```text
Claude Code / Codex = Strong Runtime Planning + Weak Long-Term Evolution
```

而 ICU-MUJICA 可以聚焦在：

```text
Execution → Reflection → Evolution
```

这段 Assistant 线基本把 User 线的“可持续自优化”扩展成系统分层。

```text
给一个 skill 和描述，让它在反馈中不断调整自己。
```

这像是对复杂 graph evolution 的反向压缩：

```text
如果只保留 skill + feedback + update，会怎样？
```

---

# 12. Assistant 线单独串读

下面把 Assistant 线从头到尾单独串起来。

---

## 12.1 一开始把 multi-agent 不满意解释成行业共性

Assistant 先强调：

```text
Agent 数量不等于智力提升。
```

然后把 v1 的不满意解释为 agent 系统普遍天花板。

它马上把用户的 skill 转向解释成：

```text
从角色模拟到能力接口化。
```

---

## 12.2 把 HDL tokenization 讨论推向 graph / IR

Assistant 把用户的 tokenizer 直觉升级为：

```text
HDL 不适合被当作 token sequence 建模。
```

随后把 AST / graph / HDL 关系说成：

```text
AST 是 syntax representation；
HDL 是 constrained dynamic graph system。
```

---

## 12.3 把用户的 HDL graph 解释成递归 computation graph

用户纠正 agent graph 误解后，assistant 把“端口是节点，逻辑是边”解释为：

```text
recursive computational graph / graph rewriting system
```

这一步给用户的 graph 直觉上了一层术语。

---

## 12.4 把可训练 skill 推成 runtime-adaptive module

Assistant 把 system prompt 微调解释为：

```text
prompt as state
runtime operational memory
policy adaptation
```

并提醒 prompt drift。

---

## 12.5 给 skill 找社区坐标

Assistant 做 skill 概念史：RL option、tool use、Voyager、prompt fragment。

然后建议初期别急着 LangGraph，而是先验证：

```text
Skill 表示 / 检索 / 组合
```

并提出 RAG for Behavior。

---

## 12.6 把 ICU-MUJICA v2 解释成 HDL Compiler + LLM Passes

Assistant 看 v2 文档后，把系统解释为：

```text
Single LLM + Skill + Workflow
```

更像 compiler pipeline。

提出：

```text
Skill = Operator
Workflow = DAG
Artifact = IR
```

---

## 12.7 把 LoRA / GRPO 讨论转成显式 Graph 路线

Assistant 区分 LoRA 学能力、GRPO 学决策。

随后提出：

```text
甚至不训练，Graph 负责记忆，LLM 负责决策。
```

这把用户从训练路线拉回结构路线。

---

## 12.8 把 memory 分成 procedural graph

Assistant 用 MemGPT / A-MEM / GAM / cognitive memory，把用户的 RAG + workspace + graph memory 解释成：

```text
Memory → Concept → Skill → Workflow
```

并把 Graph Memory 定位成行动结构。

---

## 12.9 把 Evaluate + Execute 推成 Decision Graph

Assistant 将 evaluate/execute 节点解释成 EDA 更合理的诊断—执行闭环。

后来又在 HDL Evolution Graph 讨论中继续升级：Evaluate 不只是分类器，而是 state extraction / interpretation / hypothesis。

---

## 12.10 把 Graph 结构优化推成 Workflow Learning

Assistant 对“复用性检查”例子的回应是：这不是学新能力，而是优化流程。

随后引入：

```text
Prompt update / Routing update / Graph update
```

以及复杂度预算。

---

## 12.11 不断提出分层，直到用户开始反感过度上升

Assistant 在多处给出分层：

- Skill / Parameter / Routing / Memory / RAG / Graph evolution；
- Foundation / Evolution layer；
- Knowledge / Workflow / Skill / Model evolution；
- System / Method / Theory paper；
- Skill Graph / Meta Graph / 双层图。

这些分层帮助整理，但也不断把问题往上推。

用户后来明确指出这种模式：assistant 总是推翻并推进新一层质疑。

---

## 12.12 被用户拉回 harness

在 Mutation 讨论中，assistant 一度提出 meta graph。

用户反驳：

```text
那是没有 harness 的 todo。
```

Assistant 接受后，把方向改成：

```text
Harness-Constrained Graph Evolution
```

这是 assistant 线被 user 线纠偏的一次关键点。

---

## 12.13 承认 LLM 倾向：擅长找漏洞，不擅长冻结问题

在目标函数对话中，assistant 承认：

```text
模型容易把设计上升成更高层问题。
```

并建议根据用户当前目标，停止继续追 mutation 本质。

---

## 12.14 抓住 Addition Graph 作为机制雏形

当用户提出 Addition Graph，assistant 把它压成：

```text
Base Graph
Execution Trace
Delta Extraction
Addition Graph
Graph Update
```

这是 assistant 线比较有帮助的一次收束：它没有继续追问“Addition 的本质是什么”，而是说它已经从概念走向机制。

---

## 12.15 把原教旨 self-improving skill 当作极简对照

最后，assistant 把单 skill 自改进解释成：

```text
single-policy self-modifying loop
```

并指出它的三个硬问题：feedback 结构化、update 空间、credit assignment。

这给复杂 graph evolution 一个更小的比较对象。

---

# 13. 两条线的互动模式

这一节不是最终结论，只是记录两条线之间反复出现的互动方式。

---

## 13.1 User 提具体机制，Assistant 往上抽象

典型例子：

```text
User: 多 system prompt 换 skill
Assistant: 角色模拟 → 能力接口化
```

```text
User: 端口是节点，逻辑是边
Assistant: recursive computational graph / graph rewriting system
```

```text
User: skill 可以微调 system prompt
Assistant: prompt as state / runtime operational memory
```

这类互动让概念更有理论感，但也容易让问题越抬越高。

---

## 13.2 User 反复用 harness 把问题拉回地面

典型例子：

```text
User: 动态 FSM 像没有 harness 的 todo agent
```

```text
User: meta graph 又变成纯 todo，没有 harness
```

这是 User 线最重要的纠偏之一。

---

## 13.3 Assistant 不断指出 hidden constraints

Assistant 常常指出：

- 可执行；
- 可评估；
- 可收敛；
- complexity budget；
- prompt drift；
- graph explosion；
- credit assignment。

这会让用户感到“我刚提出一个东西，又被推翻”。

但这些 hidden constraints 后来确实变成系统边界的一部分。

---

## 13.4 User 越来越明确自己不想要什么

User 线逐渐排除：

- 纯 multi-agent；
- 纯 AST；
- 纯 workflow graph；
- 纯 todo graph；
- 纯 linter evaluate；
- 纯 training；
- 过定义 mutation；
- 没有 harness 的 meta graph。

这些排除项比最终正定义更早稳定。

---

## 13.5 Assistant 从质疑者转向整理者的节点

在最后 Addition Graph 出现后，assistant 不再继续无限追问，而是把它整理成机制：

```text
Execution Trace → Addition Graph → Graph Update
```

这可能是两条线互动里比较重要的一次转变：assistant 从“推高问题”变成“压实机制”。

# 14. 双线压缩版

# 15. 这份双线版对应的后续用途

这份文档比较适合用来做三件事：

1. **回看用户自己的思路不是随机发散，而是不断通过反例收束。**
2. **回看 assistant 哪些地方有帮助，哪些地方把问题推得太高。**
3. **写论文 intro / method 时区分“作者原始动机”和“对话中形成的系统化解释”。**

如果之后继续写正式文档，可以把两条线压成：

```text
User motivation:
ICU-MUJICA v1 的 multi-agent harness 能用但难以持续改进。
因此 v2 尝试用 skill / graph / harness feedback 表示可迭代的 EDA agent workflow。

System framing:
Graph 内部保持欠定义，但 graph boundary、execution contract、harness feedback 强定义。
系统从 execution traces 中抽取 addition graph，用于更新后续 skill graph / workflow。
```

但这只是后续论文式压缩。当前这份双线版先保留过程。
