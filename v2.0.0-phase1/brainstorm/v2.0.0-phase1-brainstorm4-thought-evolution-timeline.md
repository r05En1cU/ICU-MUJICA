# 1. 2026-05-29 06:22 — 从 v1 完结开始，先出现的是“不满意 multi-agent”

对应文件：`ICUMUJICA Agent 完结_6700b73a878a (2).md`

这一段的起点不是 Graph Evolution，而是比较朴素的项目状态分享：

- ICU-MUJICA Agent v1 完结；
- 项目全称里 `M` 原来主要指 Multi；
- v1 是 multi-agent / multi-docker / harness 风格；
- v1 “能用”，但成效不够满意；
- 用户对当前系统的感觉是：分工明确，但性能仍很受限于 LM 本身。

当时讨论里先出现了一个判断：

```text
Agent 数量 ≠ 智力提升
```

这不是最终路线，但它影响了后面很多选择。因为如果多 agent 只是多个 system prompt 互相传话，那它带来的更多是：

- 状态隔离；
- 工具职责固定；
- context 压缩；
- harness 化流程；

而不是模型能力本身的提升。

这里开始出现一个迁移方向：

```text
multi-agent / 多 system prompt
    ↓
skill / capability interface
```

当时的语气还不是“我要做一个可进化系统”，更像是：

> 既然多 agent 的边界不稳定，不如把能力边界接口化。

这时候 skill 的含义还比较工程化：

- 不是人格化 agent；
- 不是“你现在扮演 verification engineer”；
- 更像一个有输入输出契约的能力模块；
- 更容易 validation、cache、replay、debug。

所以第一层变化大概是：

```text
角色模拟
    ↓
能力接口化
```

这个变化后来会不断变形，但它先给 v2 定了一个方向：v2 不再主要追求“更多 agent”，而是追求更稳定、更可组合、更能被工程验证的 skill / workflow。

## 1.1 HDL 表示问题开始插入进来

同一份记录里，讨论后来从 Agent 组织方式转到了 HDL 本身。

用户提出的判断是：

```text
tokenize 的语言对 HDL / HD 不太合适
```

随后又进一步说：

```text
比起 AST，graph 更合适；HDL 的 tree 属性没有那么强。
```

这一段里，HDL 不再只是“被 agent 写出的代码”，而开始被当成一种结构系统：

- AST 只能描述语法树；
- HDL 关键的是 signal dependency、dataflow、state transition、timing path；
- Tree 的单父节点、层级包含假设，在 HDL 里经常被 fanout、reconvergence、feedback loop、cross-module dependency 打破；
- 所以 HDL 更像 constrained dynamic graph system。

用户进一步给出了一个更具体的 graph 直觉：

```text
端口是节点，逻辑是边，边又可分为节点和边，直到 sequential 为止。
```

这句话后来非常重要。因为它不是普通 workflow graph，而是在说 HDL 本身可以被表示成递归可展开的 computation graph：

```text
port / signal endpoint = node
logic relation = edge
edge can be decomposed into subgraph
sequential element = cut boundary / termination point
```

当时还没有把它叫做 Evolution Graph，但已经出现了几个后面反复回来的元素：

- Graph 不是装饰，而是 HDL 的语义表示；
- sequential element 作为边界；
- combinational logic 作为可展开结构；
- AST 只是 syntax shell；
- skill 可能是 graph 上的操作，而不是普通 tool。

## 1.2 “可训练 skill”先以 system prompt 微调的形式出现

这一段里，用户还提出：

```text
可训练的 skill 是不是一个好主意？
这里的训练不是梯度下降，而是对话过程中微调 System Prompt。
```

当时这个想法还很 prompt engineering，但里面已经有了后面 evolution 的影子：

- Skill prompt 不是静态配置；
- prompt 本身可以被视为系统状态；
- 根据失败、trace、verification、用户反馈去修改 skill prompt；
- 这像 runtime operational memory；
- 也像 policy adaptation / execution heuristic evolution。

这时的“进化对象”还很小：

```text
Skill Prompt
```

但已经开始问：

```text
Skill 的训练到底更新什么？
```

当时列出来的可能更新对象包括：

- execution policy：先检查什么、怎么 retry；
- attention bias：哪些风险优先；
- context shaping：哪些信息保留，哪些压缩；
- routing preference：哪些子 skill / tool 更可信。

这跟后来讨论 graph mutation 时的多层优化对象能接上。只是这里还停在 skill 内部；后面会逐渐扩展到 graph、memory、RAG、routing、harness。

## 1.3 “切成臊子”和小粒度 skill / Semantic MOE

同一段后面，用户提到“切成臊子”。

这不是玩笑式表达而已，它其实把 skill 粒度问题说出来了：

```text
monolithic agent
    ↓
small reusable skills
```

随后出现了另一个后面会反复出现的想法：小粒度 skill 方便做类似 MoE 的东西。

当时它还不是模型结构层面的 MoE，而更像：

```text
Semantic / Structural MOE
```

- expert = skill operator；
- router = task / graph region / problem type；
- activation basis = HDL semantic locality；
- 一个任务只激活某个 clock domain、timing path、module subtree、dependency cone。

这里的思路还没有进入 Graph Evolution，但它给出了一个很实际的约束：

> 如果 skill 太大，不能局部验证、局部优化、局部替换；如果 skill 足够小，才有可能产生 routing、selection、evolution。

所以到 5 月 29 日这一份记录末尾，已经有了几条线：

```text
multi-agent 不满意
    ↓
skill 化
    ↓
小粒度 skill
    ↓
HDL graph 表示
    ↓
skill 作为 graph / HDL 结构上的局部算子
```

这还不是最终体系，但后面几天基本是在不断重排这些元素。

```python
class Skill:
```


## 4.1 Memory 变成分层结构，不只是向量库

用户随后提出：

```text
RAG 做长期记忆，sharedworkspace 和 project 单次对话 md 做中短期记忆，中间插入 Graph 记忆。
```

这时记忆系统被分成了三层：

```text
长期记忆：RAG / Vector DB
中短期记忆：workspace / project md
中间层：Graph Memory
```

Graph Memory 的作用不是存事实，而是存关系和流程：

```text
问题类型
    ↓
解决范式
    ↓
适用条件
    ↓
验证步骤
```

这让 Memory Graph 和 Skill Graph 靠近了。

当时用认知科学的三类记忆来解释：

```text
Episodic Memory: 发生过什么
Semantic Memory: 学到了什么
Procedural Memory: 怎么做
```

Procedural Memory 开始接近 Skill。

所以这时产生了一个层次结构：

```text
Memory Node
    ↓ abstraction
Concept Node
    ↓ abstraction
Skill Node
    ↓ composition
Workflow Node
```

这不是最终结构，但它让“RAG 只是长期记忆”这个想法升级了：

```text
RAG 存事实和案例
Graph 存范式和路径
Policy 决定怎么走
```

## 4.2 Evaluate + Execute 第一次比较清楚地作为 graph node 类型出现

用户接着提出：

```text
Graph 的 node（skill 类型）可以是 evaluate + execute 两类组合。
Evaluate 返回问题类型和位置，然后根据类型和位置决定执行哪类 execute。
```

这一步非常重要。因为 graph 不再只是 skill 链：

```text
Skill A → Skill B → Skill C
```

而变成：

```text
Evaluate
    ↓ recommend / diagnose
Execute
    ↓ produce patch / workflow / result
Verify / Evaluate again
```

当时 Evaluate Node 的输出可以是：

```yaml
confidence
findings
location
suggestions
```

甚至可以输出多个 hypothesis，而不是单一类型：

```yaml
hypothesis:
  - candidate: setup_violation
    score: 0.81
  - candidate: fanout_issue
    score: 0.67
```

这时 ICU-MUJICA 的 graph 已经开始像诊断—治疗系统，而不只是 action flow。

也出现了一个三层信息分工：

```text
Workspace: 现在发生了什么？
RAG: 以前发生过什么？
Graph: 接下来通常该做什么？
```

这句话后来其实能解释很多设计选择。

## 4.3 “不能做”的东西被推出 Memory，推向 Linter / Rule Layer

同一份记录里，用户提到老师说 memory 里可以存能做和不能做的东西，但用户感觉不能做的东西喂给 LLM 效果反而不好，应该做进自定义 Linter，作为硬约束。

这一步把系统从纯 LLM 记忆往工程约束推了一下。

当时区分了两类“不能做”：

```text
客观上绝对不能做 → Linter / Checker / Formal / Rule Layer
经验上通常不要做 → Memory / RAG / Graph Memory
```

最后形成了四层：

```text
Rule Layer: 不犯硬错误
Memory Layer: 记住过去
Graph Layer: 组织经验
Policy Layer: 决定路径
```

这一层次对后面 mutation / evolution 很重要。因为它说明不是所有反馈都该变成 prompt，也不是所有经验都该进 graph。

有些约束应该是不可协商的：

```text
if violation:
    reject()
```

而不是让 LLM “记住不要这么做”。

# 5. 2026-06-04 12:42 — Graph 结构优化开始接近“进化”的工程定义

对应文件：`Graph结构优化思路_d29c305bf8ca (2).md`

这份记录从一个很具体的例子开始：

```text
LLM 输出 RTL 功能完备，但缺少模块复用。
用户反馈后，系统询问是否需要检查模块复用/可配置性，并加入 graph 节点作为设计初期评估 skill。
```

这时讨论把它叫作：

```text
Graph 结构优化 / Workflow Learning
```

而不是 skill capability learning。

理由是：LLM 不是不知道 parameterization / reuse，而是没有在流程里主动做。因此学习对象更像：

```text
知道但没做
    ↓
以后在合适条件下记得做
```

这时第一次较清楚地区分了：

- 新能力；
- 新评估步骤；
- routing 条件；
- workflow 结构。

并且开始警惕 Graph 爆炸：如果每个反馈都新增节点，系统很快会变成 300 个 evaluator。

---

## 5.1 “进化”被暂时定义成性能提升和复杂度增长之间的关系

用户提出：

```text
在不发生系统复杂度爆炸的情况下，性能能得到提高，我觉得这是一种进化。
```

这一段给 evolution 一个比较工程化的方向：

```text
Evolution Score ≈ ΔPerformance / ΔComplexity
```

它不是理论定义，但当时很有用，因为它把“进化”从单纯“长出新节点”拉回到复杂度预算。

随后提出三层更新成本：

```text
Level 1: 参数 / Prompt 更新
Level 2: 策略 / Routing 更新
Level 3: 结构 / Graph 更新
```

其中：

- Prompt 修改成本最低；
- Routing 条件变化成本较低；
- 新增 node / subgraph 成本最高；
- 新增 skill 更昂贵。

这一段的重要移动是：

```text
Graph evolution 不一定意味着 Graph 变大。
```

很多时候更好的 evolution 是：

- 改已有 skill prompt；
- 改触发阈值；
- 改 routing 条件；
- 改 RAG 优先级；
- 淘汰无用 memory；
- 最后才新增 graph node。

这给后面 mutation 的层次化打了基础。

---

## 5.2 Evolution 的对象从 Graph 扩展到 Skill / Parameter / Routing / Memory / RAG

用户随后说，优化可以包括：

- Skill prompt；
- Graph 结构；
- 定期调整参数；
- RAG 内增加/减少代表性项目；
- 只保留 top 项目作为优先参考。

于是系统优化对象变成：

```text
System
├── Skill
├── Graph
├── Memory
├── RAG
├── Routing
└── Parameters
```

这里 evolution 不再是“graph edit”一个动作，而是一个多层更新过程：

```text
Experience
    ↓
Analysis
    ↓
Optimization Action
    ↓
System Update
```

这个框架后来会在 mutation 讨论中继续出现。

比较重要的是，RAG / Memory 也可以 evolution：

- 保留 top 项目；
- 按使用频率、成功率、recency 调整权重；
- 对不同 task type 使用不同历史案例；
- 忘掉长期没用的记忆。

这时“遗忘”也被当成进化的一部分，而不是只增加。

## 5.3 可持续性、Minimal Core、模型能力负相关复杂度

用户说“至少是可持续的”。

这一段讨论转向长期维护：

- agent 系统很容易从 5 个 skill 长到 50 个 skill；
- prompt、tool、memory、graph 都会积累技术债；
- 复杂度增长速度如果超过性能收益，系统会退化。

因此出现一个偏架构的想法：

```text
Minimal Core + Generated Layer
```

长期固定的只有：

```text
LLM
Skill Runtime
Graph Runtime
Memory
```

## 7.1 Cross-layer Mapping 成为比 Graph 本身更有价值的部分

讨论里很快指出：Graph 在 EDA 里并不新。

- RTL dependency graph；
- logic cone graph；
- timing graph；
- module hierarchy graph；
- placement graph。

更少被 agent 直接利用的是跨抽象层 traceability：

```text
RTL
  ↕
Netlist
  ↕
Physical
  ↕
Timing
```

例如工程师看到：

```text

```

真正想问的是：

- 哪条路径？
- 对应 netlist 哪些 cell？
- 对应 RTL 哪段代码？
- 是哪个 synthesis / mapping / placement 操作造成？
- 有没有某次 optimization 引入副作用？

这时 Evolution Graph 更像：

```text
Git for Hardware Design Objects
```

节点不是文件，而是设计对象：

- RTL signal；
- expression；
- netlist cell；
- placement region；
- timing path。

边是 transformation：

- mapped_to；
- placed_at；
- timing_affects；
- optimized_from。

这条线给 HDL Agent 一个独特方向：不是只会调用工具，而是能 reason over design evolution。

```text

```

或者：

```text

```

图不只是静态 knowledge graph，而是 dynamic / executable graph。

```text
知道大概长什么样，但不知道基本操作是什么。
```

不过当时也已经有一些负约束：

- 不是参数进化；
- 不是模型微调；
- 进化对象是结构；
- 需要 harness 验证；
- 不想退化成 todo graph；
- 不想靠纯 LLM judge。

所以准确状态更像：

```text
有一个值得研究的核心假设，但还没有找到最小形式。
```

这引出了一个下一步问题：

```text
Minimum Evolvable Graph 是什么？
```

---

## 9.4 Addition Graph：第一次从概念明显落到机制雏形

这份记录最后，用户提出：

```text
skill graph 做备份，然后当前任务的多次迭代过程中根据反馈优化重复工作流的部分。
然后新增的 node 命名为 addition graph。
```

这一段很重要，因为它比“mutation 是什么”更具体。

它给 graph update 一个 data source：

```text
Execution Trace
```

结构可以写成：

```text
Base Graph / Skill Graph
    ↓
Execution Trace（当前任务多轮执行轨迹）
    ↓
Diff / Delta Extraction（找重复、无效、新增步骤）
    ↓
Addition Graph / Patch Graph
    ↓
Graph Update
```

这里出现了三个对象：

```text
Skill Graph: 稳定知识 / 长期可复用结构
Execution Trace: 动态过程 / 当前任务实际行为
Addition Graph: 从 trace 抽出的增量结构 / patch / candidate update
```

这比抽象 mutation 更接近可实现系统，因为它回答了：

```text
Mutation candidate 从哪里来？
```

答：从执行轨迹、重复 workflow、失败/成功反馈中抽取。

同时它有压缩动机：

```text
把反复出现的执行片段压缩成可复用 graph update
```

它也留下了三个待定点：

- addition graph 是 graph patch，还是 new skill induction，还是 second-order graph？
- 优化目标是 step 数、token cost、success rate、稳定性还是泛化？
- feedback 来自 LLM judge、HDL simulator、compile pass/fail 还是 heuristic checker？

但整体上，这一步已经从“Graph Evolution 是愿景”推进到“从 execution trace 提取 reusable graph update”。

这可能是截至这批记录里最接近方法雏形的一步。

# 10. 2026-06-07 07:20 — 原教旨 self-improving skill：在图之外又提出极简版本

对应文件：`天马行空的想法分析_54ff47ee245c (2).md`

最后一份记录是用户说有点天马行空。

一开始描述为：

```text
工具链自由化的方法，或者类似某种训练的方法。
```

这被拆成几类：

- program synthesis / DSL search；
- RL / policy over tool use；
- compiler / IR evolution；
- constrained self-modifying system；
- implicit program induction。

但用户随后说明，自己说的是更笼统、更原教旨的方案：

```text
给一个 skill，一开始只是描述它要做的事；
让它在反馈过程中不断自己优化、调整这个 skill。
```

这其实把系统压到一个极简 loop：

```text
Skill S_t
    + Task D
    ↓
Execute → Action / Output A_t
    ↓
Feedback F_t
    ↓
Update Skill → S_{t+1}
```

这一版甚至不需要 graph、planner、multi-agent、固定 decomposition。

它保留三样东西：

```text
skill
execution
feedback
```

因此它可以被看成：

```text
minimum viable self-improving agent loop
```

这个想法和 Addition Graph 有点不同：

- Addition Graph 是从多步执行 trace 抽取 graph update；
- 原教旨 self-improving skill 是单 skill 自我改写；
- 一个偏结构压缩，一个偏 policy / prompt 自修改。

它的问题也比较明确：

- feedback 必须结构化，否则 prompt drift；
- skill update 空间太大，需要约束 representation；
- credit assignment 弱，单纯成功/失败不知道该改哪一步。

这份记录像是对前面复杂 graph 路线的一次反向检查：

> 如果把 graph / planner / meta structure 全拿掉，最小自改进回路还能不能成立？

它没有替代 Evolution Graph，但给了一个下界：至少 self-improving skill 这个最小版本是可以做的，只是稳定性和收敛性需要验证。

# 11. 按思路移动来看的几个连续变化

下面不是强结论，只是把时间线上反复出现的移动放在一起，方便后面继续写论文/设计文档时查。

---

## 11.1 从 Agent 数量到能力接口

最早的不满是 multi-agent 效果不够好。

移动大致是：

```text
多 Agent / 多 system prompt
    ↓
角色边界不稳定
    ↓
Skill / Capability Interface
    ↓
Skill Protocol / Operator / Pass
```

这个移动没有消失。后面不管 Graph Evolution 怎么变，skill 仍然作为一种能力边界存在。

---

## 11.2 从 Skill Library 到 Skill Graph

Skill 一开始是 prompt fragment / context transformer / tool + prompt。

后来因为 skill 数量会增加、会组合、会依赖、会冲突，于是自然出现 graph：

```text
skills/
    ↓
skill retrieval
    ↓
skill dependency / routing
    ↓
skill graph
```

但这个 graph 一开始可能不需要 LangGraph。可以从 markdown skill + retrieval 做起。

---

## 11.3 从 Skill Graph 到 Evaluate/Execute

单纯 Skill A → Skill B → Skill C 太像 action flow。

EDA 任务里常常先要诊断，再执行：

```text
Evaluate
    ↓
Problem / Location / Hypothesis
    ↓
Execute
    ↓
Verify / Evaluate
```

这里 Evaluate 起初像 classifier，后来被升级成 interpretation / hypothesis / world model construction。

---

## 11.4 从 Memory 到 Graph Memory / Procedural Memory

RAG 不只是存文档。

逐渐形成：

```text
Workspace: 当前上下文
RAG: 历史案例和事实
Graph Memory: 工程范式和行动结构
Policy: 如何选择路径
```

这让 memory 和 skill 开始汇合：procedural memory 近似 skill / workflow。

---

## 11.5 从 Graph Optimization 到 Evolution

最开始的 graph update 例子是“复用性检查”。

随后 evolution 被暂时用工程方式理解：

```text
性能提升
    /
复杂度增长
```

因此不鼓励无脑新增 node。更优先：

1. prompt / 参数更新；
2. routing 条件更新；
3. memory / RAG 权重更新；
4. graph 结构更新；
5. 新 skill。

这让 evolution 和 sustainability 绑在一起。

---

## 11.6 从 Everything Evolves 到 Stable Core + Mutable Layer

用户一度想让系统自组织，但后来承认基础 planning 需要预设。

于是出现：

```text
Foundation Layer: Observe / Plan / Execute / Evaluate / Learn
Evolution Layer: skill, routing, graph, memory, prompt, evaluator criteria
```

这一步避免系统去 mutate 自己的全部架构。

---

## 11.7 从 Static Graph 到 Evolution / Lineage Graph

HDL graph 不是新东西，关键变成跨层映射和演化历史：

```text
RTL object
    ↓ synthesis / mapping / placement / optimization
Netlist / physical / timing object
```

这里 Evolution Graph 是 design lineage，不只是 workflow graph。

它主要服务：

```text
为什么变成这样？
```

而不只是：

```text
现在是什么？
```

---

## 11.8 从 State Transition 到 Harness-Constrained State Transition

State → Transition → State 一度看起来能统一很多东西。

但用户指出 dynamic FSM / todo graph 不可持续。

所以必须加：

```text
Verifier / Harness / Invariant
```

也就是：

```text
State Transition + State Validation
```

对于 HDL 来说，harness 很自然：compile、simulation、formal、timing、PPA。

---

## 11.9 从 Mutation Taxonomy 到 Graph 欠定义

用户后来不想过度定义 mutation。

更稳的方向是：

```text
强定义 Graph 边界 / 合法性 / Harness
弱定义 Graph 内部变化 / mutation 形式
```

这样避免把优化空间提前锁死。

---

## 11.10 从 Graph Evolution 愿景到 Addition Graph 机制

最后比较接近方法雏形的是：

```text
Base Skill Graph
    ↓
Execution Trace
    ↓
Repeated / Useful Substructure Extraction
    ↓
Addition Graph / Patch Graph
    ↓
Graph Update
```

这一版有几个可抓住的点：

- mutation candidate 来自 trace，不是凭空想；
- feedback 经过 harness；
- update 可以是 graph patch / new skill / compressed workflow；
- 目标可以是减少重复、提升成功率、降低成本、增强稳定性。

---

# 12. 当前记录里比较像“保留下来的设计约束”

这里仍然不写成最终定论，只列出这些记录里反复没被完全推翻的约束。

1. **HDL/EDA 场景不太适合纯 text / token flow。**  
   至少需要 graph / IR / artifact / report / trace 这些结构化对象参与。

2. **Skill 比人格化 agent 更适合作为能力边界。**  
   但 skill 可以是 prompt、tool、procedure、operator、pass，不必一开始规定死。

3. **Graph 本身不够，必须有 execution 和 feedback。**  
   没有 harness 的 graph 很容易变成 todo graph。

4. **Evaluation 不能只做 linter，也不能完全靠 judge。**  
   可能需要 Rule Layer + Graph Query + LLM Interpretation + Verifier 的组合。

5. **进化不应该等于复杂度单调增长。**  
   修改已有组件、调整 routing、遗忘低价值 memory，可能比新增 node 更像健康 evolution。

6. **Mutation 不宜被过度枚举。**  
   更适合定义 graph validity、boundary、observability、rollback、fitness，而不是预定义所有 mutation type。

7. **EDA 的自然优势是有 harness。**  
   Compile / Simulation / Timing / PPA 这些反馈让 selection 比通用 agent 任务更可落地。

8. **Graph Evolution 目前更像研究方向，Addition Graph 更像方法雏形。**  
   前者提供愿景，后者提供 execution trace → graph update 的可能机制。

# 13. 如果下一步继续推进，可能比较自然的写法

这不是计划，只是从时间线里看，比较顺的落点可能是：

```text
ICU-MUJICA v2 starts from a skill-based HDL agent framework.

Instead of treating workflow as a fixed hand-written graph,
it records execution traces under an EDA harness,
extracts reusable repeated substructures,
and turns them into incremental graph updates.

The graph is deliberately under-specified internally,
while its boundary, execution contract, and evaluation harness are explicit.
```

中文可以写得更松一点：

```text
ICU-MUJICA v2 暂时不把重点放在预先设计一个完整 workflow graph，
而是保留一个可执行、可验证的 skill graph 作为基础结构。

系统在具体 HDL 任务的多轮执行中记录 trace，
利用编译、仿真、lint、PPA 等 harness 反馈判断哪些执行片段反复有用，
再把这些片段压缩成 addition graph / graph patch，
用于更新后续任务中的 skill routing 或 workflow structure。

Graph 的内部变换不被过度定义，
但 Graph 的边界、合法性、执行契约和反馈接口需要相对清楚。
```

这段表述暂时避开了“mutation 的终极定义”，也没有把 Evolution Graph 抬成过强理论。它更贴近这几天实际思路移动出来的东西。
