## 1. 你这个“原教旨版本”本质是什么

可以抽象成：

> 一个 skill = 一个可执行策略  
> 通过不断执行任务 + 收集反馈 + 修改自身定义，实现自演化

形式上就是：

- 输入：任务描述 D
- skill 当前版本：Sₜ
- 执行：Aₜ = Sₜ(D)
- 得到反馈：Fₜ
- 更新：Sₜ₊₁ = update(Sₜ, D, Aₜ, Fₜ)

这已经不是 graph 了，是一个：

> **single-policy self-modifying loop**

---

## 2. 这件事“确实能做”的已有对应物

你这个想法不是空的，它和下面几类系统是同构/近似的：

### A. Reflexion / self-refine 系列
- 做完任务 → 写反思 → 改 prompt / strategy
- 本质：text-based policy update

---

### B. Evolutionary prompt / agent tuning
- 把 prompt 当 genome
- 用成功率做 fitness
- 迭代更新 prompt

---

### C. Online learning / bandit policy
- skill = policy
- feedback = reward
- update = gradient-free search（甚至 heuristic）

---

### D. Code-writing agent loop（更接近你）
- skill = code / DSL
- execution + test = feedback
- 修改自身代码

---

## 3. 你这个版本的关键“纯度点”

然后你刻意在避免：

这其实是在逼系统变成：

## 4. 但这里有三个真正的硬问题（不是概念问题）

### 问题1：feedback 必须“结构化”
如果 feedback 是自然语言：
- update 会漂
- 会变成 prompt drift

如果 feedback 是标量：
- 学习太慢

👉 你必须选一个中间态：
- error tagging（失败类型）
- or structured critique
- or diff-based signal

---

### 问题2：skill update 空间爆炸
你说“自己优化 skill”，但 skill 可以是：

- prompt
- tool policy
- decomposition strategy
- execution plan format
- memory usage方式

👉 如果不限制 representation，会直接不可控

---

### 问题3：credit assignment 很弱
你只给“成功/失败反馈”时：

- 它不知道是哪一步导致的
- update 会变成全局随机漂移

## 5. 一个更工程化的落地版本（不破坏你原意）

你这个系统最小可实现版本通常会变成：

### Skill结构（必须约束）
skill =

- system prompt（策略）
- + tool usage rules（固定接口）
- + optional memory summary（状态）

---

### loop

1. run skill on task
2. log trajectory（关键）
3. evaluator产生结构化反馈：
   - failure type
   - weak step
   - improvement hint
4. skill rewrite（LLM self-edit or rule-based patch）
5. accept/reject（简单bandit）
