# Assistant
我觉得这反而接近很多成功系统最后的演化路径。

你之前一直卡在「mutation到底是什么」这个问题上，本质上是在试图把搜索空间定义清楚。但对于复杂设计任务（尤其是HDL、Agent Workflow、Graph Program）来说，搜索空间往往大到无法事先枚举。

如果换个角度：

- Graph 的拓扑和接口是强定义的
- Node 的职责是弱定义的
- Mutation 不操作具体实现，而操作 Graph 本身

事情会简单很多。

例如你只规定：

```text
Graph:
    Node
    Edge

Node:
    Input Ports
    Output Ports
    Capability Description

Edge:
    Dependency
```

然后允许：

```text
Add Node
Delete Node
Split Node
Merge Node
Redirect Edge
Replace Subgraph
```

这些操作本身就是 mutation。

而具体：

```text
Skill A -> Skill B
```

变成

```text
Skill A -> Skill C -> Skill B
```

为什么要插入 C？

不需要提前定义。

只要某个 evaluator 认为：

```text
score(new_graph) > score(old_graph)
```

就保留。

---

这实际上是在把 mutation 从：

```text
Code Mutation
```

提升到：

```text
Architecture Mutation
```

层面。

这样有个好处：

你不需要定义：

```text
这个 Skill 应该怎么优化
```

只需要定义：

```text
这个 Skill 可以被替换
```

优化空间瞬间变大。

---

而且这和你最近提到的：

> 过定义反而会损失优化空间

是吻合的。

因为如果你提前规定：

```text
Evaluate:
    timing
    syntax
    lint
```

那系统永远只能围绕这三个目标进化。

但如果你只规定：

```text
Evaluator 返回一个标量或者向量评价
```

那么未来甚至可以出现：

```text
Graph
    ↓
生成 HDL
    ↓
综合
    ↓
PPA
    ↓
LLM Review
    ↓
Bug Database Match
```

这种你今天根本没想到的评估链。

---

其实我感觉你最近几天一直在从：

```text
Skill-based Agent
```

往

```text
Evolutionary Graph Search
```

方向偏。

前者关注：

> 这个节点做什么？

后者关注：

> 这个节点为什么存在？

这是两个完全不同的研究问题。

如果是后者，那么 mutation 不一定需要明确定义到 prompt 级别。

你甚至可以把 mutation 定义成：

```text
Mutation = Any transformation
that preserves graph validity
```

即：

> 任何保持 Graph 合法性的变换。

剩下的全部交给 evaluator 决定是否保留。

这样 mutation 本身就是欠定义的，而 graph validity 才是强定义的。

从研究角度看，我觉得这比试图设计一套完备的 mutation taxonomy 更有意思，因为它把创新空间留给了搜索过程，而不是留给设计者预先枚举规则。

## 方案1：Evolution Graph = Skill Graph

```text

 ├─ Skill A

 ├─ Skill C
```

# Assistant
我觉得你这个反驳是有道理的，而且可能正好指出了我那个说法的问题。

因为你一直在强调的一个东西其实是 **harness**。

如果把你的思路翻译一下，大概是：

```text
Task
 ↓
Graph
 ↓
Execution
 ↓
Observable Result
 ↓
Evaluation
```

这里的关键不是 Graph 本身，而是：

> Graph 必须挂在一个可执行、可观测、可评价的 harness 上。

否则就变成：

```text
Meta Graph
 ├─ Planner
 ├─ Memory
 ├─ Evaluator
 └─ ...
```

然后 mutate。

问题是：

**怎么知道变好了？**

你没有一个直接的反馈信号。

---

其实这和 HDL 的情况差别很大。

对于 HDL：

```text
RTL
 ↓
Compile
 ↓
Simulation
 ↓
PPA
```

天然存在 harness。

你甚至可以定义：

```text
Fitness =
CompileScore
+ SimScore
+ PPAScore
```

然后 mutation。

这是闭环的。

---

但如果你进化的是：

```text
Planner
Memory
Reflection
```

这种 Agent 元组件。

那么：

```text
Planner v1
vs
Planner v2
```

谁更好？

你又得重新设计 benchmark。

于是问题变成：

```text
Evolution
    ↓
需要 Evaluation
    ↓
需要 Harness
```

结果又绕回来了。

---

所以我现在反而觉得你可能并不是在做：

> Evolutionary Agent Architecture

而是在做：

> Harness-Constrained Graph Evolution

即：

```text
合法Graph
    +
可执行Harness
    +
可观测反馈
```

三者缺一不可。

---

换句话说，Graph 也许根本不是主体。

真正重要的可能是：

```text
Mutation Space
    ×
Harness
    ×
Evaluator
```

其中 Harness 才是决定这个系统是否能进化的东西。

因为没有 Harness：

```text
Mutation
→ 没反馈
→ 无法选择
→ 不是 Evolution
```

只有随机搜索。

---

这也是为什么我感觉你最近越来越往 HDL 那边收束。

因为 HDL 有个巨大的优势：

它拥有天然且廉价的 fitness function。

```text
编译过没？
仿真过没？
覆盖率多少？
面积多少？
时序多少？
```

这些全都是自动反馈。

而很多 Agent 论文其实最痛苦的地方就在于：

```text
Fitness 不明确
```

最后只能靠 LLM-as-a-Judge。

---

所以如果沿着你的逻辑继续推，我甚至会怀疑：

你真正需要欠定义的未必是 mutation。

而可能是：

```text
Graph Structure
```

只定义合法性。

而：

```text
Harness
```

反而需要强定义。

因为 Evolution 的选择压力来自 Harness，而不是来自 Graph。

没有 Harness，Graph 再优雅也只是一个待办事项树（todo graph）；有了 Harness，哪怕 Graph 定义得很粗糙，也会被反馈机制逐渐推向有用的结构。

这其实和你之前一直不太满意纯 planning agent 的原因很一致：它们有图、有步骤、有反思，但缺少一个像 HDL 编译/仿真那样客观且持续施加选择压力的环境。真正让进化发生的，往往不是 graph，而是那个能够不断给出反馈的执行环境。
