# ICU-MUJICA v2.0.0 Phase 1 Brainstorm 1 Vision

> 日期：2026-06-04  
> 阶段：phase 1 vision 收束与工程边界梳理  
> 状态：brainstorming，但 v2 的核心方向已经基本确定

## 当前共识

ICU-MUJICA v2 不再沿用 v1 的多 Docker、多 Agent、多人格协作路线。v2 的主线应明确收束为：

```text
Single LLM
+ Harness
+ Multi-skill Runtime
+ Explicit Workflow
+ Layered Memory
+ IC / HDL Tool Feedback
```

也就是说，v2 不是继续堆叠 Agent，而是把原本多 Agent 系统中已经隐约出现的 skill 化趋势显式化。

v2 的目标也不应被描述成通用 Coding Agent。更准确的定位是：

```text
面向 IC / HDL 设计流程的可进化 Multi-skill 自动化系统
```

它更接近：

```text
HDL Compiler
+ LLM Passes
+ Skill Library
+ Workflow Runtime
+ Evolution Engine
```

而不是：

```text
Planner Agent
+ Coder Agent
+ Verifier Agent
+ Debug Agent
```

phase 1 的重点不是一次性实现完整自进化系统，而是先建立一个稳定的最小核心，使后续 skill、workflow、memory、RAG 和 graph 结构可以被持续修改、评估和回滚。

## Phase 1 中“可进化”的暂定定义

本阶段不把“可进化”定义为模型参数训练，也不要求 LoRA、GRPO 或在线梯度更新。

phase 1 中的进化暂定为：

```text
系统根据用户反馈、工具反馈或执行失败记录，
更新 skill 定义、prompt、routing policy、RAG 引用、graph memory 或 evaluator，
并在后续同类任务中自动复用这些更新，
同时控制复杂度增长。
```

因此，phase 1 的进化载体主要包括：

- `Skill Definition`：skill 的描述、prompt、输入输出约束、执行策略。
- `Evaluator`：新增或调整检查维度，例如复用性、参数化、CDC、时序风险。
- `Routing Policy`：什么类型的任务触发什么 skill / evaluator。
- `Graph Memory`：保存“某类问题适合怎样处理”的流程范式。
- `RAG Index`：保留、降权或提升对某些历史项目 / 经验案例的引用。
- `Linter / Checker Rules`：将客观禁止项沉淀为硬约束。

phase 1 暂不把以下内容作为必要目标：

- 训练底层 LLM 参数。
- 自动重写核心 runtime。
- 让系统自由修改 planning 框架本身。
- 追求完全自主的 open-ended self-improvement。

## 稳定核心与可变层

v2 需要明确区分不可频繁变化的核心系统，以及可以通过经验持续调整的可变层。

### 稳定核心

稳定核心应由人工设计并保持相对固定：

```text
Harness Runtime
Planning Runtime
Skill Runtime
Evaluation Runtime
Memory Runtime
Artifact Runtime
Tool / Linter Runtime
```

这些部分更像操作系统或编译器框架，负责：

- 管理会话与项目状态。
- 组织多轮分析与执行。
- 加载和校验 skill。
- 调用工具链与 linter。
- 管理 workspace 和 artifacts。
- 记录 trace、feedback 和经验。

### 可变层

可变层允许被用户、实验或 evolution engine 调整：

```text
Skill Definitions
Skill Prompts
Evaluator Criteria
Workflow Templates
Routing Policies
Memory Entries
RAG Ranking
Graph Memory Edges
Linter Rule Sets
```

这意味着 v2 的长期目标不是让系统越来越大，而是让系统能够在复杂度预算内保留有效组件、淘汰无效组件、重组已有组件。

一个重要原则是：

```text
优先修改已有组件，最后才新增组件。
```

例如用户反馈“RTL 功能正确但复用性差”时，系统更新优先级应是：

```text
1. 调整 RTL generation skill prompt
2. 调整 reuse evaluator 的触发条件
3. 调整 RAG / graph memory 中相关案例权重
4. 在 workflow 中插入已有 reuse evaluator
5. 只有前面都不够时，才新增 skill / node
```

## 当前目录结构的主要问题

README 中的原始目录计划大致是：

```text
ICU-MUJICA
|- src
|  |- common
|  |- skill
|  |  |- graph
|  |  |- evaluate
|  |  |- execute
|  |- workflow
|- workspace
|- output
|  |- frontend
|  |- backend
|- docker_compose.yml
|- requirements.txt
|- .env
```

这个结构抓住了 Harness、Skill、Workflow、Evaluate、Execute、Workspace、Output 等关键词，但目前还把不同层次的概念放在了相近位置。phase 1 应把它们重新分层。

### 1. `skill`、`workflow`、`evaluate`、`execute` 的关系需要收束

`evaluate` 和 `execute` 不建议作为 `src/skill` 下的两个顶层类别存在。更确定的表述是：

```text
Skill 是能力单元。
Evaluate / Execute / Verify 是 skill 或 workflow node 的运行角色。
Workflow 是多个 skill / node 的编排方式。
```

因此，一个 skill 可以是：

```text
Evaluator Skill
Executor Skill
Verifier Skill
Procedure Skill
```

也可以采用组合形式：

```text
Evaluate
 -> Execute
 -> Verify
```

对于 IC / EDA 场景，这个闭环比单纯的 action chain 更自然。

例如：

```text
STA Report
 -> EvaluateTimingViolation
 -> ExecuteTimingFix
 -> RunSTA
 -> VerifyTimingResult
```

### 2. `graph` 需要区分三种含义

当前文档中的 `graph` 容易混淆。v2 至少会涉及三类 graph：

```text
HDL Graph
Skill / Workflow Graph
Memory Graph
```

三者不是同一个东西。

#### HDL Graph

HDL graph 是硬件描述本身的结构表示。根据当前 vision，它更接近：

```text
port / signal 作为节点
logic relation 作为边
边可以递归展开为子图
递归边界停止在 sequential element
```

这属于 HDL / EDA 的语义 IR，不是 Agent workflow graph。

#### Skill / Workflow Graph

Skill / workflow graph 描述 skill 之间的调用、依赖、触发条件和执行顺序。

例如：

```text
Requirement Analysis
 -> Port Inference
 -> RTL Generation
 -> Reuse Evaluation
 -> Simulation
```

#### Memory Graph

Memory graph 记录历史经验之间的关系，例如：

```text
FIFO task
 -> CDC failure pattern
 -> CDC evaluator
 -> async boundary fix procedure
```

它回答的不是“现在代码是什么结构”，而是“过去类似问题通常如何处理”。

因此不建议继续使用单一的 `skill/graph` 表达所有图结构。

### 3. `common` 应拆成明确的基础设施目录

`common` 容易演化成万能目录。phase 1 应避免把协议、schema、runtime、工具函数都塞进去。

建议明确拆分为：

- `schemas/`：Pydantic 模型、skill 输入输出、artifact 描述、memory record。
- `protocols/`：skill lifecycle、evaluate / execute / verify 协议、message contract。
- `runtime/`：session、workspace、artifact、trace、state 管理。
- `utils/`：真正无业务语义的小工具。

### 4. `workspace` 和 `output` 应被视为运行状态与产物

`workspace` 是 active project / active session 的工作区。`output` 更适合改名为 `artifacts`。

phase 1 中建议明确：

```text
workspace/   # 中短期项目状态、工作目录、单次运行上下文
artifacts/   # 生成产物、报告、RTL、testbench、log、trace
```

这两个目录通常应被 `.gitignore` 忽略大部分生成内容，只保留必要说明文件。

### 5. `frontend/backend` 需要换成更贴近 IC flow 的命名

虽然 IC design flow 中也有 frontend / backend 说法，但在仓库结构里容易被误解成 Web 前后端。

建议 artifacts 采用更直接的 IC / EDA 命名：

```text
artifacts/
|- design/          # spec、architecture、RTL
|- verification/    # testbench、simulation、coverage
|- synthesis/       # synthesis scripts、netlist、timing reports
|- reports/         # summaries、review reports、evaluation records
|- traces/          # execution trace、feedback record、skill invocation log
```

### 6. 需要显式加入 memory 和 linter 的位置

根据当前 vision，memory 与 linter 不是附属功能，而是 v2 的核心工程边界。

Memory 分层建议：

```text
Long-term Memory      -> RAG / historical projects / stable knowledge
Mid-term Memory       -> project md records / shared workspace summaries
Short-term Memory     -> current session state / active context
Graph Memory          -> problem-pattern-skill-workflow relationships
```

Linter / checker 负责沉淀硬约束：

```text
客观禁止项 -> Linter / Checker
经验偏好项 -> Memory / RAG / Graph Memory
```

例如多 driver、组合环、CDC 直接采样、锁存器推断等，不应主要依赖 LLM 记忆，而应尽量变成 rule / checker。

### 7. Skill 的定义资产和运行代码必须分离

Skill 在 v2 中不只是 Python 函数。它至少可能包含：

- name / description
- trigger / routing hints
- prompt / instruction
- input_schema / output_schema
- evaluator criteria
- execution policy
- verification policy
- cost / latency / confidence metadata
- linked RAG / memory references

因此建议区分：

```text
skills/                  # skill 定义资产，适合迭代和版本化
src/icu_mujica/skills/   # skill runtime、loader、registry、executor
```

这使后续“skill 进化”主要发生在 definition layer，而不是核心 runtime layer。

### 8. `.env`、Docker Compose 和依赖管理需要工程化

建议：

- 使用 `.env.example`，真实 `.env` 加入 `.gitignore`。
- 使用 `compose.yml` 或 `docker-compose.yml`，避免 `docker_compose.yml`。
- phase 1 可以先用 `requirements.txt`，但建议尽早引入 `pyproject.toml`。

如果项目会形成包结构、测试、lint、类型检查和命令行入口，`pyproject.toml` 会更稳。

## Phase 1 最小闭环

phase 1 不应先实现完整 SkillGraph、完整记忆系统或自动进化框架。更稳妥的验证闭环是：

```text
User Spec
 -> Harness 创建 session
 -> Workspace / project md 记录中短期上下文
 -> Planning 选择一个固定 workflow
 -> Skill Runtime 加载 skill definition
 -> Evaluator 定位问题或生成检查建议
 -> Executor 生成 RTL / patch / testbench / script
 -> Verifier / Linter / Tool 进行验证
 -> Artifact Runtime 保存结果与 trace
 -> Memory Runtime 记录失败模式、修复方式和触发条件
 -> 后续同类任务自动触发相关 evaluator / routing
```

这个闭环的重点是证明三件事：

1. `Evaluate -> Execute -> Verify` 能提高 IC / HDL 任务稳定性。
2. 经验可以从一次任务沉淀为后续 routing / evaluator 的触发条件。
3. 增加经验不会导致 skill、prompt、memory 和 workflow 无限制膨胀。

## Phase 1 的进化成本层级

为了避免复杂度爆炸，建议为不同类型的系统修改设置成本优先级。

```text
Level 1: Skill prompt / metadata update
Level 2: Routing condition / threshold update
Level 3: RAG / memory ranking update
Level 4: Workflow edge / graph memory update
Level 5: New evaluator / executor / verifier skill
Level 6: Core runtime change
```

原则：

```text
能用低层修改解决的问题，不进入高层修改。
```

这能让“进化”更接近可持续优化，而不是无限堆节点。

## 暂定结论

当前 phase 1 的确定性已经比最初目录草图更高。v2 的关键不是“把目录分得更细”，而是明确系统分层：

```text
稳定核心层：Harness / Planning / Skill Runtime / Memory Runtime / Evaluation Runtime
可变定义层：Skill Definitions / Workflow Templates / Routing Policies / Prompts
记忆经验层：RAG / Project Markdown / Graph Memory / Execution Trace
硬约束层：Linter / Checker / Tool Feedback
产物状态层：Workspace / Artifacts
领域结构层：HDL Graph / IC Flow Semantics
```

因此，phase 1 的工程路线应从以下最小假设开始：

```text
IC / HDL 任务可以被拆成小粒度 skill。
小粒度 skill 可以通过 Evaluate / Execute / Verify 闭环稳定执行。
执行经验可以沉淀为 routing、evaluator、prompt、RAG 或 graph memory 的更新。
这些更新可以在复杂度受控的情况下提升后续同类任务表现。
```

如果这个假设成立，ICU-MUJICA v2 才有继续扩展到 SkillGraph、分层长期记忆、自定义 RAG、自动 evaluator 生成和更复杂 evolution engine 的价值。

当前最重要的收束点是：

```text
先证明经验能改变后续 workflow，而不是先实现完整自进化框架。
```
