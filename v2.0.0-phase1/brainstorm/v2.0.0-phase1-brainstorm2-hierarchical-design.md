# ICU-MUJICA v2.0.0 Phase 1 Brainstorm 2 Hierarchical Design

> 日期：2026-06-05
> 主题：记录 ICU-MUJICA 的各个模块的分层次设计想法
> 状态：brainstorming for hierarchical design

## 分层次设计主线

考虑到 ICU-MUJICA v2 的功能实现和具体设计，认为有必要对其分层次设计进行探讨，以得到详细的技术定义。

ICU-MUJICA 的分层次设计主要由以下主链构成：

- [1] Agent 主链；
- [2] HDL 生成主链；
- [3] 前仿主链；
- [4] 后仿与优化主链。

以下各部分将分别对上述主链展开探讨。

## Agent 主链

### Agent 子链初步划分

当前将 Agent 子链暂定划分为三个主要部分：

```text
Agent Chain
|- Harness
|- SkillGraph
|- RAG & Memory
```

这个划分可以作为 Agent 主链的第一版分层骨架。其重点不是继续沿用 v1 的多 Agent 人格分工，而是把 v2 中实际有效的 Agent 工程能力拆成三个更稳定的系统层：运行控制、能力编排、经验与上下文管理。

#### 1. Harness

Harness 是 Agent 子链中的稳定运行核心，负责把不稳定的 LLM 能力约束在可观察、可回放、可验证的执行框架内。

Harness 暂定职责包括：

- 管理 session、task、workspace 与 artifacts；
- 维护多轮对话与任务状态；
- 调用 LLM、skill、workflow、tool 与 checker；
- 记录 trace、日志、失败原因与用户反馈；
- 控制 retry、rollback、human-in-the-loop 与异常恢复；
- 为后续 skill、workflow、memory 更新提供执行证据。

从分层角度看，Harness 不应承载具体 IC / HDL 专业能力。它更像运行时和调度壳层，负责让系统稳定执行，而不是直接定义系统会什么。

##### Harness 链内部职责

Harness 链当前进一步拆分为五类初步职责：

```text
Harness
|- 系统管理
|- 上下文管理
|- 权限与配置信息管理
|- 记忆结构管理
|- 自优化机制
```

###### 1. 系统管理

系统管理是 Harness 的基础运行职责，负责维持 ICU-MUJICA 在一次任务或一个项目周期内的可执行状态。

暂定包含：

- session / task 生命周期管理；
- workspace 初始化、加载、清理与隔离；
- artifacts 的生成、索引、归档与引用；
- LLM、tool、skill、workflow、checker 的调用入口；
- 运行状态、错误状态和中断恢复；
- trace、log、checkpoint 与 replay 支持。

这一部分应保持为稳定核心，不宜频繁被自优化机制直接修改。它更像系统的执行底座。

###### 2. 上下文管理

上下文管理负责决定在某一轮 LLM / skill / workflow 调用中，系统应该暴露哪些信息、压缩哪些信息、隐藏哪些信息。

暂定包含：

- 当前用户目标与任务状态；
- 项目级设计上下文；
- 当前 workflow node 的输入上下文；
- tool output / linter output / simulation log 的压缩摘要；
- RAG 检索结果的注入与裁剪；
- memory 记录的选择性加载；
- 上下文窗口预算与优先级控制。

上下文管理是 Agent 效果的重要来源之一。其目标不是把所有信息塞给 LLM，而是在有限上下文预算内提供最可能改变输出质量的信息。

###### 3. 权限与配置信息管理

权限与配置信息管理负责控制系统可以访问什么、修改什么、调用什么，以及在不同任务模式下采用哪些运行参数。

暂定包含：

- 模型供应商、模型名称、温度、token budget 等 LLM 配置；
- tool / EDA command / shell / file access 的权限边界；
- workspace、artifacts、memory、RAG index 的读写权限；
- 用户确认策略，例如是否允许自动修改 workflow、skill prompt 或 memory；
- 环境变量、密钥引用与外部服务配置；
- 不同运行模式，例如 explore、execute、review、repair、benchmark。

这一层是 Harness 的治理边界。对于 phase 1，权限与配置管理不需要过度复杂，但应尽早避免把模型配置、工具权限和用户确认策略散落在各个 skill 内部。

###### 4. 记忆结构管理

记忆结构管理负责定义、维护和访问 Memory 的结构，但不等同于 Memory 内容本身。

换句话说，Harness 管理的是：

```text
memory schema
memory lifecycle
memory read / write policy
memory update trigger
memory conflict / decay / pruning policy
```

而 RAG & Memory 层保存的是具体知识、案例、项目摘要、失败模式和经验关系。

暂定包含：

- long-term / mid-term / short-term memory 的边界；
- project memory、session memory、failure memory、graph memory 的 schema；
- 什么事件会写入 memory；
- 写入前是否需要 evaluator 或用户确认；
- memory 如何降权、过期、合并或删除；
- memory 如何影响 skill routing、workflow selection 和 RAG retrieval。

这一职责位于 Harness 与 RAG & Memory 的交界处。Harness 不应把记忆内容硬编码进运行逻辑，但需要提供稳定的结构与更新协议。

###### 5. 自优化机制

自优化机制负责根据用户反馈、工具反馈、执行 trace 和 memory 记录，提出或执行对系统行为的改进。

暂定优化对象包括：

- skill prompt / instruction / metadata；
- skill routing policy；
- workflow edge / trigger condition；
- RAG ranking / reference priority；
- memory entry 的新增、合并、降权或删除；
- evaluator / checker 的触发条件；
- 必要时新增 skill 或 workflow node。

自优化机制需要遵循复杂度预算，避免每次失败都通过新增节点解决。当前倾向采用以下优先级：

```text
1. 修改已有 skill prompt / metadata
2. 修改 routing condition / threshold
3. 调整 RAG / memory ranking
4. 调整 workflow edge / trigger condition
5. 新增 evaluator / executor / verifier skill
6. 修改 Harness core runtime
```

从职责边界看，自优化机制可以由 Harness 触发和执行，但不应让 Harness 自由改写自身核心运行逻辑。phase 1 更适合先实现“可记录、可建议、可人工确认”的自优化，而不是完全自动的 open-ended self-improvement。

##### Harness 链筛选结论

上述五类职责中，phase 1 的优先级可暂定为：

```text
必须具备：系统管理、上下文管理、基础配置管理、trace 记录
需要设计接口：记忆结构管理、自优化机制
可以延后完整实现：复杂权限系统、自动 graph learning、自动 runtime 修改
```

也就是说，Harness 链在 phase 1 的目标应是先形成稳定、可观察、可回放的执行底座，并为 memory 与自优化留下明确接口，而不是一开始就实现完整的自主进化系统。

#### 2. SkillGraph

SkillGraph 是 Agent 子链中的能力与流程层，用于统一描述 skill node、skill subgraph 与 workflow graph 的组织关系。

Skill 表示可调用、可评估、可组合的能力单元；Workflow 表示多个 skill 在具体任务中的执行顺序、依赖关系与触发条件。

这一层暂定包含：

- skill definition；
- skill prompt / instruction；
- input / output schema；
- skill routing policy；
- workflow template；
- workflow graph / DAG；
- evaluate -> execute -> verify 生命周期；
- skill 执行结果的评分、复用与失效判断。

当前倾向于将 Skill 和 Workflow 放在同一子链下讨论，是因为二者在 v2 中高度耦合：Skill 是节点能力，Workflow 是节点组织方式。许多所谓 Agent 能力提升，实际上不是新增模型能力，而是调整 skill 选择、触发条件或 workflow 结构。

因此，这一层应重点回答：

```text
面对某类 IC / HDL 任务，系统应该调用哪些 skill，按什么顺序调用，在什么条件下插入评估、修复或验证节点。
```

##### Skill 与 Workflow 的 graph 关系

当前进一步思考认为，Workflow 本质上是以 graph 形式组合的 skill 设计。

也就是说，Workflow 不是一个独立于 skill 的外部流程脚本，而是对多个 skill node 的组织方式：

```text
Workflow Graph
|- Node: Skill / Skill Subgraph
|- Edge: dependency / trigger / transition condition
|- State: artifacts / context / evaluation result
```

在这种定义下，Skill 不一定必须是不可再分的原子函数。一个 Skill 可能有两种形态：

```text
Atomic Skill
	一个最小可调用能力单元

Composite Skill / Skill Subgraph
	一个可以展开为小型 workflow graph 的能力单元
```

例如，一个 `RTL Generation Skill` 表面上是一个 skill node，但它内部可能包含：

```text
Analyze Requirement
	↓
Infer Interface
	↓
Generate RTL
	↓
Evaluate RTL Quality
	↓
Repair RTL
```

因此，Skill 可能是一个可扩展、可分裂的 node 设计：

```text
Skill Node
	↓ expand when needed
Skill Subgraph
```

这个设计的价值在于：普通任务可以把 skill 当作单个节点调用；复杂任务或失败场景下，Harness / Workflow Runtime 可以将该节点展开成更细粒度的子图，以获得更好的可观察性、可干预性和可优化性。

##### Evaluate-Execute 作为最小 skill graph

如果采用 evaluate -> execute 的反馈流程，那么最小可运行单元可能不再是单个 skill，而是一个小型 graph。

最基本形式为：

```text
Evaluate
	↓
Execute
```

对于 IC / HDL 任务，更完整的形式通常会变成：

```text
Evaluate
	↓
Execute
	↓
Verify
```

这意味着一个 skill 的执行生命周期可以被视为一个内部 subgraph，而不是单次 LLM 调用或单个函数调用。

例如：

```text
Evaluate Reusability
	↓
Improve Parameterization
	↓
Verify Interface Compatibility
```

这里 `Evaluate Reusability`、`Improve Parameterization`、`Verify Interface Compatibility` 可以分别是独立 skill，也可以作为一个 composite skill 的内部节点。

##### 解耦 evaluate 与 execute 的必要性

虽然 evaluate -> execute 是一个自然闭环，但并不意味着所有 evaluate 和 execute 都必须一一配对。

实际 workflow 中可能出现更灵活的结构，例如：

```text
Evaluate 1
	↓
Execute 1
	↓
Execute 2
	↓
Evaluate 2
```

这种结构对应的含义是：

- 第一个 evaluator 负责识别任务类型、风险或缺陷；
- 多个 executor 分阶段执行修复、生成或转换；
- 后置 evaluator 再判断结果是否满足目标；
- 中间不要求每个 executor 后都立即有一个 evaluator。

例如 HDL 生成任务可能是：

```text
Evaluate Requirement Completeness
	↓
Execute Interface Design
	↓
Execute RTL Generation
	↓
Evaluate RTL Reusability / Synthesizability
```

又例如前仿 debug 任务可能是：

```text
Evaluate Failure Log
	↓
Execute Waveform Hypothesis
	↓
Execute RTL Patch
	↓
Evaluate Simulation Result
```

因此，phase 1 不宜把 Skill 定义写死为固定的 evaluate-execute pair。更合适的定义是：

```text
Skill 是可组合节点。
Evaluate / Execute / Verify 是节点角色。
Workflow 是节点及其角色之间的 graph 编排。
Composite Skill 是可被当作单节点调用的小型 workflow graph。
```

##### Skill 粒度与分裂策略

如果允许 skill node 被扩展或分裂，需要控制粒度，否则 workflow graph 会迅速复杂化。

初步可采用以下分裂原则：

```text
只有当一个 skill 内部出现可复用子步骤、可独立评估风险、或经常失败的局部流程时，才考虑将其分裂为 sub-skill / subgraph。
```

暂定触发条件包括：

- 某个 skill 在 trace 中反复失败；
- 用户反馈集中指向 skill 内部某个局部质量问题；
- 该 skill 内部步骤可以被其他 workflow 复用；
- 该 skill 的输入输出已经复杂到难以验证；
- 需要对某个中间产物进行 tool / linter / checker 验证。

反过来，如果一个 subgraph 长期只在单一场景使用，且没有独立评估价值，则可以保留为 composite skill 的内部过程，不必提升为全局 workflow node。

##### 初步筛选结论

这一设计适合作为 SkillGraph 层的核心思想，但 phase 1 应避免直接实现复杂的动态 graph expansion。

更稳妥的路线是：

```text
Phase 1:
	支持固定 workflow template
	支持 skill lifecycle 中的 evaluate / execute / verify 角色
	记录 composite skill 的内部 trace
	暂不要求运行时自动拆分 skill node

Phase 2+:
	根据失败记录和用户反馈，建议 skill 分裂或 workflow edge 调整
	在人工确认后新增 sub-skill / subgraph
	逐步支持可控的 graph expansion
```

也就是说，当前应先把“skill 可以是 subgraph”作为概念模型和 trace 结构保留下来，但实现上先从固定模板和显式定义的 composite skill 开始。

#### 3. RAG & Memory

RAG & Memory 是 Agent 子链中的经验与上下文层，负责让系统从历史项目、用户反馈、工具输出和失败案例中获得可复用信息。

这一层暂定包含：

- 知识型 RAG：规范、手册、历史设计、测试数据、工具文档；
- 项目记忆：当前项目的设计决策、接口约定、阶段性总结；
- session 记忆：当前任务的短期状态、问题记录与待办；
- failure memory：失败模式、根因、修复方法和触发条件；
- graph memory：问题模式、skill、workflow 修改之间的关系；
- feedback memory：用户反馈如何影响后续 routing、prompt、workflow 或 RAG 权重。

这一层需要避免变成无限增长的上下文垃圾堆。RAG & Memory 的价值不在于保存所有内容，而在于筛选出能改变后续行为的经验。

更准确地说，Memory 不应主要保存“模型不能做什么”这类软约束；客观禁止项和确定性规则应尽量沉淀到 linter / checker 中。Memory 更适合保存：

```text
过去什么任务在什么条件下失败，后来通过什么 skill、workflow 或约束修改得到改善。
```

### 三者关系

Agent 子链的初步运行关系可以表示为：

```text
User / Spec
	↓
Harness
	↓
SkillGraph
	↓
Tool / Linter / Checker / LLM Execution
	↓
Harness Trace
	↓
RAG & Memory Update
	↓
影响后续 Skill Routing / Workflow / Prompt / Retrieval
```

其中：

- Harness 负责执行闭环和状态管理；
- SkillGraph 负责能力组织和任务流程；
- RAG & Memory 负责提供历史上下文，并在执行后吸收有价值经验；
- Tool / Linter / Checker 提供硬反馈，避免所有判断都停留在 LLM 自评层面。

### 初步筛选结论

这个三分法适合作为 phase 1 的 Agent 主链分层起点。

原因是它保留了 v1 Agent 系统中已经有效的 Harness 工程经验，同时把后续 v2 的重点转向更可维护的 skill 化系统，而不是继续增加独立 Agent 数量。

暂定判断如下：

```text
Harness          -> 稳定核心层
SkillGraph       -> 可变能力与流程层
RAG & Memory     -> 经验与上下文层
```

这一分法也有助于控制“可进化”系统的复杂度：

```text
优先更新 skill prompt / metadata
其次更新 routing policy / workflow edge
再次更新 RAG / memory ranking
最后才新增 skill node 或修改 core runtime
```

### 待继续讨论的问题

- Harness 是否只负责运行时，还是也负责 evolution policy 的执行？
- Skill definition 和 workflow definition 是否需要与 runtime code 分离存放？
- Workflow graph 是否在 phase 1 中只做固定模板，暂不做动态 graph learning？
- RAG 与 Memory 是否需要在代码目录和概念模型中进一步拆开？
- 用户反馈进入系统后，应优先修改 prompt、routing、RAG 权重、workflow edge，还是新增 skill？
